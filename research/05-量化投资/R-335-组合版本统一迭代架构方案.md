## 一句话版本（用户读第一段就懂整个方案）

**给「A 腿 + gold 腿 + 中央风控参数」这个三元组合发一个版本号 `vC-x.y`，让组合成为系统里的一等公民对象（与引擎版本、registry 版本并列）**。从此小市值因子迭代、旧引擎升级、新增引擎、调整风控模型、调整权重口径，**统统只是生成一个新 `vC` 候选版本的不同入口**——它们都走同一条流水线：生成组合候选 → 组合回测 → 组合门禁 →（可选影子）→ 用户批准 → paper 指针切换。每一次迭代只产出一样东西：**一张成绩单（组合回测成绩 + 门禁逐条通过/不通过原因）**。「最终模拟实盘的是什么版本」从此一句话可答：**就是当前 paper 指针指向的那个 `vC-x.y`**。

## 1. 问题诊断（把用户痛点翻译成系统缺陷）

用户的三句原话，对应三个系统级缺陷。每条都给出既有文件/行号证据。

### 缺陷① 两条版本线并存、无统一身份

系统里实际存在两套互不认识的"版本"概念：

| 版本线 | 载体 | 语义 | 自动化程度 | 证据 |
|---|---|---|---|---|
| **registry 版本线** | evolution_pipeline 的 registry | 单引擎候选版本，状态机 `candidate→pending→active→sota→retired`，g1-g6 门禁，PASS 即 `_do_activate` 自动激活 | **全自动** | task-0501-notes.md 证据3：pipeline 1605 行，五操作 backtest/evaluate/activate/rollback/override，GATE_CONFIG（L57-65），STATUS_ENUM |
| **engines.json 引擎线** | 多引擎状态机（schema_version 1） | 引擎实例的运行态登记：engine A status=active、A2=sub_engine_overlay status=shadow、layer3.tabs 声明"引擎→UI Tab"映射 | **半自动**（人工/脚本维护） | task-0501-notes.md 证据3：task-0464 快照；gold 引擎不在快照清单=状态机与真实在役集存在滞后风险 |

两条线的汇流点证据：R-320 D6 记录**进化双轨双 cron 并行**（`p3_3_evolution_standalone.py` 半月 cron vs `evolution_pipeline.py` 周六 cron）——同一功能、两条版本线各自维护。用户"不知道最终模拟实盘的是什么版本"的直接根因就是：**没有一个对象把"registry 里哪个版本 + engines.json 里哪条引擎线 + 风控参数"绑定成一个可指认的整体**。

### 缺陷② 组合只存在于风控层2 的补位规则（事后叠加，非一等公民）

组合当前不是对象，是**运行时记账公式**。R-318 层2 组合净值 `NAV_L2 = A_total + sleeve_value`（`backfill_notional = total_A × (1 − ddc_scale)`）是独立进程的账面计算，只写 `results/layer2/`；组合的"存在"依附于 ddc 状态机触发（满仓且受控净值回撤 ≤−0.20 → ×0.5，回补 ≥−0.05，T 收盘判定 T+1 生效，R-316 源码 :528-540 实查）。组合的"历史"散落在回测脚本的参数组合里（F6/F7），没有版本号、没有状态机、没有成绩单载体。**想对组合做一次迭代，没有任何对象可创建、可回测、可比较**。

### 缺陷③ paper 运行态 = 三元组但无对象代表它 → 版本身份缺失

当前模拟实盘的"版本"实际上是三个互不隶属的东西拼起来：

| 腿/层 | 实际对象 | 证据 |
|---|---|---|
| A 腿 | paper_engine.py（70504B）+ registry entry `a13_rsraw_e1f10dz` + timing_internal=true | R-318 基线事实表 / task-0501-notes 证据3 |
| gold 腿 | paper_engine_gold.py（16474B），status=active_paper（08-25 批准） | R-318 基线事实表 |
| 中央风控 | ddc 阈值 0.20/降仓 0.5/回补 0.05 + 层2 补位 + 权重口径（F6/F7 待拍板） | R-316 §二 / R-317 F7 |

没有任何 `composite` 对象指向这一整组。所以用户问"最终模拟实盘的是什么版本"时，答案只能是一段需要手工拼装的描述，且每次描述都可能不一致。**版本身份缺失 = 无法有机迭代的组合层原因**（组件层已有 registry 版本机制，组合层没有）。

> 口径声明：任务书沿用早期"五门禁 IC/ICIR/turnover/容量/相关性"表述，但在役代码实测为 g1-g6（ICIR_IS=0.5 / ICIR_OOS p=0.05 / max_corr=0.7 / DSR=0.95 / logic 非空 / MDD 恶化≤2pp 一票否决，task-0501-notes 证据3）。本报告**以在役 g1-g6 为组件级现状**，任务书"五门禁"视为早期规划口径；组合级新增维度在第 4 节另列。

## 2. 组合版本对象定义（本方案的心脏）

### 2.1 Schema 草案（JSON）

```json
{
  "composite_id": "vC-1.0",
  "version": "vC-1.0",                          // 组合版本号，全局唯一，对外唯一身份
  "created_at": "2026-08-27T22:53:00+08:00",
  "motivation": "smallcap_factor_iter",          // 迭代类型，见第 3 节枚举
  "components": {
    "equity": { "type": "registry_ref", "registry_entry": "a15_rsraw_e1f10dz", "engine": "A" },
    "gold":   { "type": "engine_ref", "engine_id": "gold", "version": "g2" }
  },
  "risk_control": {
    "ddc": { "dd_thresh": 0.20, "dd_reduce": 0.5, "dd_recover": 0.05, "self_feedback": true },
    "layer2": "central_backfill_v1",             // 补位规则版本：只补 ddc 释放部分（R-318 易错点约束）
    "weighting": "f7a_50_50_base",               // 权重口径：F1/F6/F7a/F7b 选择器化
    "timing_policy": "a_timing_internal"         // A 腿择时层策略版本
  },
  "status": "candidate",                          // 见 2.2 状态机
  "parent_composite": "vC-0",                     // 来源组合（迭代链可回溯）
  "backtest_report_ref": "results/05-量化投资/R-3xx-xxx.md",
  "gate_report": { "component_level": {}, "composite_level": {} },
  "paper_since": null                             // 非空=当前模拟实盘指向它
}
```

要点：**组合版本号 `vC-x.y` 是用户唯一需要记住的标识**；组件版本号（registry entry / gold engine 版本）只出现在详情层。`parent_composite` 把每次迭代连成链，天然形成"迭代轨迹"（对应 task-0501-notes 中已有散点可视化的数据源）。

### 2.2 状态机

```
candidate → 组合回测 → 组合门禁 → 影子(可选) → 用户批准 → paper 指针指向 → 归档
    ↑          │           │          │            │          │
    └── 修改 ──┘           └── 不通过 ─┘(带原因列表)   └─(拒绝)→ 归档(附原因)
```

- **candidate**：由某迭代类型触发（第 3 节），绑定组件指针 + 风控参数集
- **组合回测**：组合级回测引擎跑出成绩单（第 4 节）
- **组合门禁**：组件级 g1-g6 照跑 + 组合级新增维度，**逐条列出通过/不通过原因**（这是用户要的"不通过原因"）
- **影子（可选）**：与在役组合并行观察 N 个月
- **用户批准**：唯一人工门，等价于现有 registry activate 的人工门语义
- **paper 指针指向**：`paper.composite_ref = vC-x.y`（第 6 节）
- **归档**：历史候选保留，可回滚

### 2.3 存放位置取舍：registry 旁新增 `composites.json`（推荐）

| 选项 | 理由 |
|---|---|
| **A. registry 旁新增 `composites.json`（推荐）** | ① registry 的 schema 是单引擎版本语义，`active` 字段被 paper 一致性徽标/准入门禁/`_do_activate` 逻辑消费，塞组合对象会污染组件语义；② 双读兼容期需要并行文件（registry 全自动线不感知组合层，先不改它）；③ engines.json 是**运行态状态机**，不适合存放版本历史与成绩单引用。缺陷：多一个落点，与 R-334 GM15「engines.json 单落点收敛」目标并存——**收敛时把 composites.json 也纳入单一读路径**（第 7 节），不冲突 |
| B. registry 内新增对象类型 `composite` | 远期统一性好（R-334 GM15 单落点收敛完成后可演进），但现阶段动 registry schema = 动在役组件语义，风险高、违背"零擅动"红线 |

结论：**现阶段选 A（并行文件），远期在 GM15 收敛时并入 registry 单一 schema 为可选演进**，不承诺、不排期。

## 3. 统一迭代类型枚举（一切变更都变成"生成候选 vC"）

任何变更 = 一个迭代类型 + 一个变更输入；生成流程完全同构：

```
变更输入 → 解析 → 生成组合候选 vC-(x.y+1) → 组合回测 → 组合门禁 → 成绩单(回测成绩+逐条原因)
```

| 迭代类型 | motivation 值 | 变更输入是什么 | 候选生成动作 |
|---|---|---|---|
| 小市值因子迭代 | `smallcap_factor_iter` | registry 新候选版本（evolution_pipeline 已产出） | 组合候选的 equity 指针改指新 registry entry，其余组件不变 |
| 旧引擎升级 | `engine_upgrade` | 引擎代码/参数补丁（如 A 腿 timing v3→v4、gold 引擎升级） | 更新对应 engine_ref 版本 + 重新组合回测 |
| 新增引擎 | `new_engine` | 新 engine_id + 初始版本（未来第三条腿） | components 增加新腿 + 权重口径重定义 |
| 中央风控参数调整 | `risk_param_tune` | ddc 阈值/降仓/回补/补位规则变化（如 0.20→0.15） | 仅改 risk_control 参数集，重跑组合回测 |
| 权重口径调整 | `weight_rebalance` | F1/F6/F7a/F7b 切换、权重比例变化 | 改 weighting 字段，重跑组合回测 |
| （未来）统一大模型替换 | `unified_model` | 路线① 的统一模型（第 5 节） | **统一模型本身成为又一个候选生成器**，产物仍是 vC 候选，走同一条流水线 |

**核心承诺**：六种变更没有任何一种走旁路。所有变更产出同一张成绩单 = 组合回测成绩 + 门禁逐条通过/不通过原因。用户只消费一个概念："这次迭代过了没有、为什么没过"。

1. **输入解析层**：新增 `composite_loader(composite_id)` —— 读 composites.json 条目，把 `components`/`risk_control` 解析为回测参数。现有 F6/F7 脚本的硬编码参数（w_A、dd_thresh、dd_reduce、补位规则）改为从对象注入

### 4.3 组合层门禁：复用组件门禁 + 新增组合维度

**组件级 g1-g6 照跑**（equity 腿复用 registry evaluate）：ICIR_IS≥0.5、ICIR_OOS p<0.05、max_corr≤0.7、DSR≥0.95、logic 非空、MDD 恶化≤2pp 一票否决——管的是"组件还能不能当组件"。

**组合级新增维度**（在 R-334 GM6 统一 gate spec 框架内注册为 composite 级判据，与 G0-G6/g1-g6 映射表并列）：

| 组合级维度 | 建议阈值（草案，待评审） | 依据 |
|---|---|---|
| 组合最大回撤 mdd | 优于或等于 parent 组合（如 F7a -6.80% 为参照线） | R-317 对照表 |
| Calmar 下限 | ≥ parent 组合（F7a 2.001 为参照线） | R-317 对照表 |

## 5. 两种组合深度对比

### 路线① 因子层深组合（gold 信号 + 小市值因子进同一统一模型，权重内生）

- **形态**：对应行业"数据→因子→策略→执行→绩效归因"五段流水线的彻底版——小市值因子与 gold 信号在模型内部融合，权重由模型内生，无显式组件边界
- **代价**：① **推倒 F6/F7 已验证研究**（R-316 156 月口径、R-317 md5 复现基线、ddc 状态机实证全部作废重做）；② **丢失引擎独立进化**（gold 引擎 08-25 刚 active_paper，冻结纪律（R-318 基线事实）被破坏，A/gold 双引擎独立演进的隔离设计 D7 失效）；③ **重做口径**（PIT/复权/涨跌停掩码/成本模型四项对齐成本，R-334 表② 已列为 qlib 迁移同等量级）
- **何时值得**：当且仅当组件间存在强交互信号（如 gold 信号能预测 A 因子表现）且已被实证——目前**无此证据**

### 路线② 组合版本对象（推荐）

- **形态**：组件独立进化（registry 线 + engines.json 线原样保留），组合层新增一等公民 `vC-x.y` 对象，组合回测引擎 = F6/F7 选择器化
- **收益**：① 改造量最小（1 个 json 文件 + 回测脚本参数化 + 前端 1 张卡）；② 直接解决版本身份问题（缺陷③ 从根上消除）；③ 组件层所有既有机制（g1-g6、registry 状态机、影子）原样复用，零推翻

### 结论与演进关系

**推荐②**。路线① 不丢弃，而是作为②框架下的**未来某次迭代类型 `unified_model`** 自然演进：当"统一大模型"被论证时，它只是又一个候选版本生成器，产物仍是 vC 候选，走同一条候选版本流水线、同一张成绩单。**②保证今天能立刻解决版本身份问题；①保证明天想深组合时不用推翻架构。**

## 9. 结论

1. **用户痛点成立且系统级**：版本身份缺失是组合层没有对象可指认的直接后果；两条版本线（registry 全自动 vs engines.json 半自动）互不认识，组合只是层2 补位公式。
2. **组合版本 `vC-x.y` 是本方案的心脏**：一个对象 = A 腿 + gold 腿 + 中央风控参数 + 权重口径 + 迭代链，状态机（候选→回测→门禁→影子→批准→paper→归档）把一切变更统一进同一条流水线。
3. **六种迭代类型（含未来统一大模型）共享同一张成绩单**：组合回测成绩 + 门禁逐条通过/不通过原因，用户消费单一概念。
4. **组合回测引擎不是从零造**：F6/F7（R-316/317）就是现成组合回测，改造=参数选择器化 + composite 输入解析 + 成绩单输出 + 门禁分两层。
5. **推荐路线②**（组合版本对象）；路线① 深组合作为未来 `unified_model` 迭代类型自然演进，不推翻架构。
6. **与 R-334 零冲突**：吸收 GM6/GM7/GM15/event_bus，独立保留 qlib 迁移/辩论代理/Mask-First/ICIR+HMM，仅提升组合层呈现优先级；「新增常驻服务 0」承诺保持。
7. **迁移 M1-M3 零风险可做，M4（paper 指针切换）需用户批准**；红线（registry active / paper_engine / HP crontab）原样沿用。
