## 1. 背景与目标

HP 量化主机系统时区为 UTC，而量化任务的心智排程普遍按 Asia/Shanghai（如"收盘后 16:30"）。需评估将 HP 时区统一为 Asia/Shanghai 的可行性、风险与实施路径。本报告回答：现状错位清单、脚本时区依赖、cron 是否支持 CRON_TZ、三条路径对比与推荐。

## 2. 方法与数据来源

## 3. 核心发现（结论先行）

1. **HP 时区确为 Etc/UTC（NTP 正常）**，cron 为 Ubuntu 官方 **Debian cron 3.0pl1-200ubuntu1**。
2. **CRON_TZ 路径实证排除**：该 cron 不支持 per-user 时区。man5 LIMITATIONS 原文："It currently does not support per-user timezones … Even if a user specifies the TZ environment variable in his crontab this will affect only the commands executed in the crontab"；man8："cron will only handle tasks in a single timezone"（守护进程只读 /etc/localtime）。
3. **crontab 内部心智已分裂**：大部分条目按 UTC 心智写（a10 注释"每月3日09:05"即 UTC），而 paper_gold daily `40 7` 是按"北京 15:40 收盘后"倒推的 UTC 表达式——同一张表两套心智，继续维持现状（路径 C）会持续踩坑；gold 评估脚本更出现把 UTC 时间戳硬标 `+08:00` 的错标（engines_shadow_evaluate_gold.py:148）。
4. **脚本层对改系统时区安全**：全部 20 个相关脚本 `utcnow=0`、无 ZoneInfo/tz_localize/Asia/Shanghai 自处理（不存在二次偏移）；裸 `datetime.now()` 共 40+ 处，用途为日志时间戳、增量 end_date 上界、去重窗口、epoch timestamp()（绝对时间不受影响）——切换后统一 +8h，无逻辑性破坏。
5. **系统面无连带**：root 无 crontab、/etc/cron.d 仅 e2scrub、systemd timers 无量化任务；常驻量化进程仅 hp_api_server.py（glibc 自动感知 /etc/localtime 变更，无需重启）。

## 4. 三条路径对比

| 路径 | 适用前提 | 风险点 | 回滚 |
|---|---|---|---|
| **A. 改系统时区** timedatectl set-timezone Asia/Shanghai + 按北京心智重写表达式 + restart cron | 脚本层审计通过（本报告已完成）；cron 需重启才读新 /etc/localtime | ① 全局生效：23 条任务绝对触发时刻整体 -8h，**必须与 crontab 重写同批原子完成**，否则语义漂移 8 小时；② 已跑进程 glibc 自动感知（hp_api_server 日志语义 UTC→北京），下游若有假设需核查；③ 历史日志/结果 ts 跨 UTC/北京两段，排查需记分界线 | 容易：恢复 crontab 备份 + set-timezone Etc/UTC + restart cron，同为一次原子操作 |
| **B. crontab 顶部 CRON_TZ=Asia/Shanghai** | cron 实现支持（cronie 特性） | **已实证本机 cron 3.0pl1 不支持**（man5/man8 原文，见发现 2）；写入后无效且易造成"已解决"错觉。换装 cronie 属引入新守护进程，量化主机不建议 | —（不适用） |
| **C. 表达式按 UTC 写死 + 注释标注换算** | 无 | 无系统变更，但心智负担永久化；**现状即 C 的无注释版且已出问题**（两套心智并存、ts 错标、凌晨心智被打破） | 无需回滚（每次只改单条） |

## 5. 结论与建议

**推荐路径 A**：系统时区改 Asia/Shanghai，同时按北京心智重写 crontab 表达式，一次 restart cron 生效。理由：B 被实证排除；C 已被现状证伪（心智分裂证据见 §3 发现 3）；A 的脚本层风险已全部审计通过，系统面无第三方依赖（root 无 crontab、cron.d/timers 干净）。

**实施步骤草案（本任务不执行；动 crontab/系统配置需用户另行批准）**：
1. 预检：`crontab -l > ~/crontab.bak-pre-tz-$(date +%Y%m%d)`；`ps` 确认无进化/采集大任务在跑；核查 collect-metrics.sh 上报 VPS 的时间字段是否 epoch（若为格式化时间，先确认 VPS 侧消费逻辑）。
2. 起草新表（北京心智，示例：半月进化保持 `0 2 1,15 * *` 恢复"凌晨低负载"本意；paper daily `30 16`→`30 15 * * 1-5`（真正收盘后）；risk_patrol `45 16`→`45 15 * * 1-5`；paper_gold daily `40 7`→`40 15 * * 1-5`（保持收盘后语义）；a10 `5 9 3` 注释与实际终于一致；月度/周末任务保持原时刻即原绝对时刻+8h 或按需微调）。
3. 原子切换：`timedatectl set-timezone Asia/Shanghai && crontab ~/crontab.new && sudo systemctl restart cron`（一次 restart 同时生效新时区与新表）。
4. 验证：`timedatectl`/`date` 显示 +0800；等下一个 `*/5` 心跳触发时刻=北京时钟整点+5；抽 logs 新时间戳跳变 8h 符合预期；确认 hp_api_server 日志时间语义切换。
5. 回滚：`crontab ~/crontab.bak-pre-tz-* && sudo timedatectl set-timezone Etc/UTC && sudo systemctl restart cron`。
6. 切换窗口建议：周六 10:00–17:00（北京）之间，周六无任何 cron 任务、距周日首批任务（03:00 verify）有数小时缓冲。

**遗留检查项（实施前）**：① collect-metrics.sh 上报字段时间格式；② VPS 侧是否按 UTC 解析 HP 上报的时间戳/日志；③ 既有 results/*.csv、state JSON 中的 ts 字段只增不改，无迁移必要。
