## 3. 核心发现（结论先行）

1. **HP 时区 = Etc/UTC**（NTP 正常，RTC=UTC）；cron 为 Ubuntu 官方 **Debian cron 3.0pl1-200ubuntu1**（vixie-cron 血统，非 cronie）。
2. **CRON_TZ 实证排除**：man5 LIMITATIONS 原文 "It currently does not support per-user timezones … Even if a user specifies the TZ environment variable in his crontab this will affect only the commands executed in the crontab, not the execution of the crontab tasks themselves"；man8："The daemon will use … /etc/localtime for the timezone … cron will only handle tasks in a single timezone"。路径 B 除非换装 cronie（量化主机不建议），否则不存在。
3. **crontab 23 条任务分裂为三组**：
   - **CST 意图 15 条**：表达式按北京心智书写，实际在 UTC 表上跑 = 全部比设计时刻晚 8 小时触发（如 paper daily 心智 16:30 → 实际北京次日 00:30；半月进化"凌晨 2 点低负载"→ 实际北京 10:00 盘中跑重计算；qfq 18:00"错峰"→ 实际北京次日 02:00，反而落在 paper daily 之后——即 R-308 发现的错峰双根因之一）。
   - **UTC 显式授权 4 条（黄金链）**：`40 7`（daily，=北京 15:40 收盘后 40 分，R-306/R-312 设计正确）、`0 3`（周日 verify=北京 11:00）、`38 9`/`40 9`（月度 append/evaluate=北京 17:38/17:40）。这 4 条是按"北京实际效果倒推"写的 UTC 表达式，**当前行为正确**。
   - **时区无关 4 条**：collect-metrics（每分钟）、heartbeat_selfheal（*/5）、notify_hub（每小时:10，去重窗口切换时一次性平移）、@reboot。
   - a12 授权文字为「HP 本地」时刻，切换后自然对齐免改；a10 注释"每月3日09:05"按 CST 心智属第一组。
4. **脚本层对改系统时区安全（无二次偏移）**：20 个相关脚本 `utcnow=0`、无 ZoneInfo/tz_localize/Asia/Shanghai 自处理；裸 `datetime.now()` 用途 = 日志时间戳 / 增量 end_date 上界（refresh_data.py:87）/ 去重窗口（notify_hub.py:213）/ epoch `timestamp()`（绝对时间，paper_engine.py:124）；gold 系列为 TZ 感知写法（paper_engine_gold.py:54 `astimezone()` 自洽）。附带发现：**engines_shadow_evaluate_gold.py:148 把 UTC 时间戳硬标 "+08:00"——现状标签即错，切换后自愈**。
5. **paper_engine 存在唯一墙钟门控（路径 C 的致命伤）**：L1357-1358 `_now_min = datetime.now().hour*60 + datetime.now().minute; if … and _now_min >= 15*60+5`（注释"已收盘(>=15:05)"=CST 语义按 UTC 时钟执行）。现状 16:30 UTC 触发时 `_now_min=990 ≥ 905` 恒过，当日行正常；若按路径 C 把表达式改写为 UTC `30 8`（想表达 16:30 CST），触发时 `_now_min=510 < 905` → 门控 FAIL → **当日行退化 T-1**，且修复必须改引擎代码（违反"不动 paper_engine"红线）。另 paper_engine.py L342/L1327 `date.today()` 两处在当前触发时点下取到的 UTC 日期恰好等于刚结束的北京交易日，行日期正确仅时间滞后。
6. **系统面无连带**：root 无 crontab、/etc/cron.d 仅 e2scrub_all、systemd timers 无量化任务；常驻量化进程仅 hp_api_server.py（glibc 自动感知 /etc/localtime 变更，无需重启进程）。

## 5. 结论与建议

**推荐路径 A，配合"分组等效改写"规则**：
- **CST 意图 15 条：表达式原样保留**（本就按北京心智书写），切换后自动回归设计时刻（paper daily 回到 16:30 CST、半月进化回到凌晨 2 点、qfq 回到 18:00 与 paper 真正错峰——R-308 双根因一次修复）。
- **黄金 4 条（UTC 显式）：等效 +8h 改写以保持现网行为**：`40 7 * * 1-5`→`40 15 * * 1-5`；`0 3 * * 0`→`0 11 * * 0`；`38 9 3 * *`→`38 17 3 * *`；`40 9 3 * *`→`40 17 3 * *`。
- **时区无关 4 条：不动**。

**实施步骤草案（本任务不执行；②③④ 需用户批准）**：
1. 预检：`crontab -l > ~/crontab.bak-pre-tz-$(date +%Y%m%d)`；确认无进化/采集大任务在跑；核查 collect-metrics.sh 上报 VPS 的时间字段格式（epoch 则无关；格式化时间需 VPS 侧核对消费逻辑）。
2. 起草新 crontab：按上述分组规则仅改黄金 4 行，其余 19 行逐字不动。
3. 原子切换：`sudo timedatectl set-timezone Asia/Shanghai && crontab ~/crontab.new && sudo systemctl restart cron`（一次 restart 同时生效新时区与新表）。
4. 验证：`timedatectl`/`date` 显示 +0800；等下一个 `*/5` 心跳触发时刻=北京时钟；抽 logs 时间戳跳变 8h 符合预期；hp_api_server 日志语义切换确认。
5. 回滚：`crontab ~/crontab.bak-pre-tz-* && sudo timedatectl set-timezone Etc/UTC && sudo systemctl restart cron`。
6. **切换窗口：避开 9/1（黄金引擎首次月度结账+调仓日），推荐 9/5（周六）白天空档**——周六全天无 cron 任务，距周日首批（verify 11:00 CST）有十余小时缓冲。
