> 评审对象：R-344《Dashboard 产品方案 PRD》(24KB) + R-342《R-336 实施级架构设计（含 Dashboard）》(34KB, v1.1)
> 评审口径：两篇构成 **PRD ↔ 实施设计** 配对，R-342 v1.1 已显式并入 R-344 对齐 4 处。评审聚焦「需求是否被忠实落地 + 设计本身的可实施性/缺口」。

## 〇、总体结论

| 维度 | 评价 | 说明 |
|---|---|---|
| 架构纪律 | ★★★★☆ | 三落点职责（HP 唯一写点 / VPS 只读镜像 / Dashboard 纯只读消费者）清晰，是整套设计最有价值的一笔 |
| PRD↔设计对齐 | ★★★★☆ | 五 Tab、引擎卡片、待处理聚合、新旧分工均已映射，对齐度良好 |
| 冻结条款遵从 | ★★★★★ | 字段名/阈值/事件类型原文引用，附专门「一致性自检」章节 |
| 可实施性 | ★★★☆☆ | 接口契约完整，但**状态机/降级闭环存在悬空，实现细节不足**（见下文 P0） |
| 风险与运维 | ★★★☆☆ | 有可用性四件套，但缺可观测性、灾备、混沌验证 |

**一句话：方向正确、边界干净，属于「设计层可以定稿，进入实现前还需补齐闭环」的水平。** 最大的风险不是某个技术选型，而是 **paper/canary 段的闭环和降级自动化的语义**——这两处若不先钉死，Phase B/C 切换时必然返工。

## 一、做得好的地方（确认保留，不建议再改）

1. **写路径唯一性是地基**。Dashboard 零写入口、人工门（G-L4）走任务中心/HP 流程——这直接封堵了"前端直改 JSON 绕过事件账本"这条 R-336 §3.1 明确要破的反模式。这个约束应在 PRD 与实施文档**双向强调**（目前 PRD 有、R-342 有，OK）。

2. **source of truth 单一**。账本(JSONL) + JSON 投影为唯一真相，SQLite 只是"可删了重建的物化缓存"——单机无 MQ/无 DB 的冻结约束被干净遵守，没有偷偷引入状态引擎。

3. **状态机含反向降级 + 禁人工改 JSON**（`live→shadow` 漂移、`live→gated` 对账失败/断路器）。这比只有正向晋升的状态机成熟一个量级。

4. **过渡三步走 + 秒级回退 + Phase D 才退役旧件**。观测能力不断档，是灰度系统该有的样子。

5. **技术栈选型有"放弃理由"**。SvelteKit/Next.js 各一条放弃依据，且复用现有 Express+node:sqlite 基建——选型决策可逆、有记录。

6. **轮询而非 SSE + 可见性节流 + `X-Ledger-Tail-Ts` 预留演进**。对月频调仓系统，这是正确的工程判断。

7. **一致性自检附录 + 修订记录（v1.1 并入 9 项用户反馈）**。设计文档的自我约束和迭代可追溯性到位。

## 二、P0 问题（建议定稿前必须解决）

### P0-1 · 状态机「自动降级」缺少触发执行者，闭环悬空
R-342 §3.3 声明：
- `live → shadow`：4 维漂移任一维**连续 2 期超带（自动）**
- `live → gated`：reconciliation.failed / 断路器 / 审计不合格

但设计同时声明 **Dashboard 零写、BFF 只读、账本只由 HP 追加**。那么：
- 谁负责在"连续 2 期超带"后**追加 `promotion.downgraded` 事件**？是 HP 上某个 watchdog/cron？还是 ddc 风控层内嵌？
- 这个执行者在 **Phase A/B 排期中是否有对应的实现动作**？（查 §5 W1-W9，未见专门条目）

**风险**：状态机图看起来完整，但自动边无人触发 → 上线后降级只能靠人工，等于退化成单向状态机。

**建议**：在 §2.2 或新增 §6.x 明确「状态迁移守护者（state guardian）」落点在 HP，列出它消费哪些事件、产出哪个事件、运行频率；并在 §5 排期补一个 W 项。

### P0-2 · canary 段「未启用」但已写进状态机，验收无定义
状态机含 `paper → canary → live` 与 canary 节点，同时 R-342 明说"canary 未启用、启用须先定义期限与失效自动降级条件"。

问题：一个**当前不存在、又未定义启用契约**的段被写进主状态机 + 前端状态图预留，会导致：
- 前端实现时不知道该节点要不要渲染逻辑；
- 未来启用时必然要改 schema/事件枚举（与"冻结条款不新造"原则轻度冲突）。

**建议二选一**：
- (a) 从主状态机图**拆出 canary 为附录/未来扩展**，主图只到 `approved → paper → live`，做到"现在能验收"；
- (b) 在 PRD 里补一份 canary 启用契约（期限、自动降级条件、G-L1..L3 阈值），让它成为真实待办而非占位。

### P0-3 · vC-0 快照的"当前在役三元组"冻结时点未定义
§3.1 / §8 Phase B 动作 1 说"首条 = 当前在役三元组（A 引擎 + gold 引擎 + ddc 风控）"，但未定义：
- 快照的 **data_cut** 取哪一天？
- 三个组件各自的 **code_hash** 如何锚定（git sha？registry 快照？）
- 若 Phase B 跨越一个调仓周期，**在役代码变更**了，vC-0 的 hash 还成立吗？

这是 `data_cut ≤ min(所有输入数据源最大时间戳)` 硬断言之外的**另一个一致性断言缺口**，直接影响"双看板对照 ≥1 调仓周期"能否成立。

**建议**：在 §3.1 补 `vC-0 构建规程`（cutoff 时刻、hash 来源、签名人/时间、是否允许补丁版本），把它当成和 `data_cut` 同等级的硬断言。

## 三、P1 问题（Phase B 实施期内解决）

### P1-1 · 双看板验收口径偏定性，缺可机器校验的差异断言
§4.7 / 里程碑 M-DB 说"NAV 口径一致、事件覆盖一致、旧看板无仅存能力（清单化）"。

**建议量化成硬门**（可写成契约测试）：
- NAV 曲线逐日差 ≤ ε（如 1bp，需先约定成本模型口径）
- 事件数 / 事件类型集合两侧一致
- 状态指针（active portfolio_version_id）一致

否则"全绿"依赖人眼比对，390px 截图基线只能验证 UI 不能验证数据。

### P1-2 · 一致性自检附录存在一处自指歧义
附录「轮询不做 SSE/WebSocket → 与 §3.3 单机无 MQ 常驻服务约束一致」。

但 §3.3 冻结条款原文是关于**事件账本存储**（不引入 MQ/DB），而 SSE 是**传输层**。两者精神一致但**条款层级不同**。将来若有人引用此条为"永不引入推送"的依据，会被误读。

**建议**：措辞改为"不引入常驻推送基础设施（不新增 MQ/WS 服务端），与 §3.3 精神一致；按需升级 SSE 的接口形态见 §4.4"。

### P1-3 · 无鉴权 = "显式设计决策"，但暴露面未量化
§3.4 声明单用户内网 + 零写面故无鉴权，反代层加 Basic Auth/IP 白名单。

缺两件事：
1. **"内网"的边界定义**——VPS 上 nginx 监听 `0.0.0.0` 还是仅 `127.0.0.1` + 反代？
2. **零写面的威胁建模**——即使只读，`/api/v1/portfolio/:id/timeline` 含 payload 摘要，若含持仓/权重，属敏感信息泄露面。

**建议**：在 PRD 或 §3.4 补"部署暴露面矩阵"（监听地址 / TLS / 反代 / 白名单 / 敏感字段脱敏）。

### P1-4 · 灾备与恢复只有一句话（"删了重建"），缺 RTO/RPO
SQLite 物化缓存可重建是真，但：
- **账本 JSONL 本身损坏/丢失**怎么办？（flock+fsync 保不了磁盘/误删）
- HP↔VPS sync cron 失败、镜像落后 > 2 自然日（即红横幅触发）后的**恢复 SOP**是什么？

**建议**：补最小灾备条款——账本每日异地副本（哪怕 rsync 到第二目录）、sync_lag 超阈的告警→人工介入 SOP、`reconciliation.failed` 的处理优先级。

### P1-5 · 可观测性不足，"可用性四件套"偏存活探针
SIGTERM 优雅关闭 / systemd 重启 / 5s 超时 / SQLite busy_timeout 都是**可用性**。但缺**业务正确性监控**：
- 重放耗时趋势（≤3s 目标是否会破）
- 增量 tail  lag
- projection_sha256_ok 失败次数
- 各 endpoint P95 延迟

**建议**：在 §4.1 或新增 §6 列出 BFF 自检指标（可与 `/api/v1/health` 合并扩展），并明确"重放失败/校验不一致 → 该端点返回 503 而非空数据"（R-342 已对初始化期有此约定，应推广到运行期）。

### P1-6 · 性能目标只有一个数据点（启动重放 ≤3s，12 个月规模）
账本增长后（2-3 年、含逐笔风险事件）性能如何？冷档合并索引的开销？

**建议**：给出**容量规划的最小公式**——热数据 12 个月行数估算、单行大小、单请求重放上限，并约定"超过则切分账本/预物化"。

| 新旧看板分工（任务/用量/报告留旧 → /legacy） | §4.7 新旧分工边界，Phase D 退役 | ✅ |
| 数据新鲜度告警 + 风险角标 | §4.3 数据新鲜度告警（sync_lag > 2 日红横幅） | ⚠️ 角标"红点"未明确端点字段 |
| 看板不负责推送，走既有渠道 | §4.3 末尾 + §4.4 | ✅ |

**唯一对齐缺口**：R-344 的"风险角标（任一待处理风险 → 红点，用户不翻页感知）"在 R-342 的 API 契约里**没有对应聚合字段**。目前 `/api/v1/health` 只返回 `reconciliation_ok`，不含"待处理风险计数"。

**建议**：`/api/v1/overview` 或 `/health` 增 `pending_risks: { count, items[] }`，由前端红点消费——这一处补上即完全对齐。
