## 一、结论先行：落地度评估

按 R-256/R-259 目标四层架构（层0 共享数据 / 层1 引擎层 N 同构 / 层2 独立中央风控 / 层3 组合呈现），逐层落地度：

| 层 | 目标 | 落地度 | 证据 |
|---|---|---|---|
| 层0 共享数据 | 采集/PIT/快照/退市，服务所有引擎 | **已落地**（复用为主，质量良好） | 数据健康页/数据资产盘点/HP→VPS 同步管道/因子页（R-256 §五 M-0.x/M-3.0） |
| 层1 引擎层 | N 同构引擎：信号+择时内化+独立 NAV+独立 registry+影子通道 | **部分落地（单引擎+半开放）** | A 引擎全链路在用；A2 已入 engines.json（shadow cross_engine）+ shadow_nav 管道 + 月度 evaluate 脚本 + 看板跨引擎影子卡（task-0465）；但前台仍只有「卡」级别，无引擎级生命周期视图；B/C 未接入 |
| 层2 中央风控 | 战略配置器+再平衡带宽+组合回撤门（哑层） | **零落地（属正常时序，非缺陷）** | 三组件机制设计已定（R-259 §六），初值全 ⏳ 留白；单引擎 w=100% 无事可做，第二引擎真金上线才激活（R-256 §四） |
| 层3 组合呈现 | Σwi×NAVi + 权重序列 + 组合回撤门 | **零落地** | 组合净值聚合页/权重时间序列/相关性矩阵均未建；对账三校验逻辑已在 HP 侧 combo_sim.py 实现（R-282 §二）但未入看板 |

**核心差距（一句话）**：数据与后端已经「多引擎就绪」（engines.json + /api/quant/engines 数据驱动遍历，不硬编码引擎 ID），但**呈现层仍是「引擎 A 单机版」思维**——用户只看得到 A 的可视化，A2/未来 B/C 是黑盒；层2/层3 因时序未激活属设计内预期，但「引擎级生命周期」「组合层视图」「层级标注」是当前就能补、且正是用户痛点的缺口。

## 三、服务端设计（API 层 + 数据契约，数据驱动）

原则：**沿 engines.json schema 遍历，不硬编码引擎 ID**；engines.json 缺失/解析失败一律降级硬编码单引擎 A（既有先例 L3683），看板永不因引擎元数据而启动失败（R-259 §4.1）。

| 端点 | 方法 | 数据契约 | 状态 |
|---|---|---|---|
| `/api/quant/engines` | GET | `{ok, available, schema_version, engines:[{engine_id,name,status,layer1,shadow,lifecycle}]}`；扩展返回 `lifecycle`（从 shadow.evals[]+audit.changes[]+registry 聚合） | **已有（L3680）**，建议扩展 |
| `/api/quant/engines/:id` | GET | 单引擎全量元数据 + `lifecycle` 状态机（当前 phase：data→factor→iterate→backtest→shadow→live） | 新增 |
| `/api/quant/engines/:id/nav` | GET | 统一 NAV 序列：active→per-engine 实盘 NAV（映射自 layer1.nav_source）；shadow→shadow_nav.csv；`{engine_id, source, frequency, points:[{t,nav,ret}]}` | 新增（shadow 已由 `/:id/shadow-nav` 覆盖，建议合流） |
| `/api/quant/engines/:id/history` | GET | per-engine 版本时间线（现 /api/quant/history 全局，加 engine_id 参数化） | 迭代 |
| `/api/quant/portfolio` | GET | 组合层：`{nav: Σwi×NAVi 序列, weights: 权重时间序列, corr: 相关性矩阵, gates: 组合回撤门状态, recon: 对账三校验}`；`layer2.enabled=false` 时返回哑层态（w=100% 单引擎）不报错 | 新增 |
| `/api/quant/portfolio/weights` | GET | 权重时间序列：目标 w（层2 配置器，季度重算+用户确认生效）vs 实际 w（漂移公式 R-259 §6.2） | 新增 |
| `/api/quant/portfolio/corr` | GET | 各引擎月度收益相关性矩阵（E1 实测 A-A2 0.135 为参考上限口径，R-282 §五） | 新增 |
| `/api/quant/portfolio/gates` | GET | 组合回撤门状态：gate_dd 触发/恢复/总敞口下限 φ 当前值 | 新增 |
| `POST /api/quant/portfolio/recon` | POST | 手动触发对账（组合 NAV=Σ wi×NAVi，阶梯函数+封闭式，tol 1e-6，对应 HP portfolio_recon.py 命令形态，R-259 §八.3） | 新增 |

契约要点：①全部组合端点接受 query 引擎集（默认遍历 engines.json 全部 active+shadow），不做全局单 A 假设；②影子期引擎无真金，组合 NAV 不含影子引擎，仅提供「影子参考组合」（固定权重试算）标注不算对账（R-259 §八.3）；③对账三校验（分解一致性/端点对账/权重守恒）结果随 portfolio 端点返回，S4 验收必跑。

## 四、前端可视化设计（看板页面目标形态）

### 4.1 引擎级生命周期视图（新增，量化页入口或复活 H2）
每个引擎一张「生命周期卡」，沿状态机阶段组织，**数据全部来自 engines.json 遍历 + per-engine 端点**：

- **数据**（层0）：该引擎数据通道新鲜度/一致性（现全局单值，需按引擎分列，R-256 M-0.3 迭代项）
- **因子/信号**（层1）：signal_desc + 因子页 per-engine 过滤
- **迭代**（层1）：per-engine registry 版本线时间线（/api/quant/engines/:id/history）
- **回测**：评分制最近裁决（overlay/adjudication verdict，R-282）
- **影子**：shadow.mode/since/min-max/clean_evals 进度条 + evals[] 明细 + 终止判据状态
- **实盘**：status=active 时 NAV 曲线 + 择时状态（timing）

**复用点（task-0468 遍历框架）**：renderCrossEngineShadowCard（L12913）已实现「遍历 engines.json shadow 引擎 → 逐个拉 shadow-nav → 渲染卡片」的完整模式，生命周期卡只需把「影子卡」泛化为「引擎生命周期卡」——同一遍历骨架，每引擎复用「卡片头部元数据+NAV 图」组件，叠加各阶段区块。模型页 v5model 组件（版本选择器/指标卡/仓位趋势图）可整体复用作实盘阶段区块。

### 4.2 组合层视图（新增，层3）
- 组合净值曲线：Σwi×NAVi（多引擎叠加，标注「层2 激活后才有意义；当前单引擎 w=100%」）

## 五、纠正点（与目标架构不符/易误导处 + 改法）

1. **A2 与中央风控的层级混淆（最易误导）**：当前影子卡无层级标注，用户易误以为 A2 是中央风控一部分（问题①）。改法：UI 明确层级标签；引擎总览用**树形结构**（A 下挂 A2=overlay 子引擎），中央风控三组件独立区块展示「等待第二引擎真金」空态——层级在数据层已正确（A2=layer1 sub_engine_overlay，cross_engine shadow），只差呈现。
2. **影子卡数据口径易误读**：A2 影子卡当前显示的是**历史基线段 2006-01→2024-06**（base_segment，R-286 §二）与 A 的对比，且 corr(A,A2)=0.999851——高相关易被误读为「影子失败」。改法：卡片标注 nav_period/source（base_segment vs 实时），并附 R-273 注记「低拥挤时代 A2≡A 属预期，clean_evals 剔无区分月，不算跟踪失败」。
3. **择时仓位趋势图的定位**：模型页「择时仓位趋势」（pos=q3z×EW-MA200，L3238/L9470）是**层1 A 引擎内化择时**，不是中央风控仓位动作。未来组合页若出现「组合仓位」概念必须与之区分，防双重砍仓误读（R-259 §6.3 先动层级/总敞口下限三规则）。
4. **engines.json A2 的 layer3.tabs 为空数组**：呈现层尚未给 A2 绑定任何 Tab——这是「黑盒」痛点的直接数据证据。改法：S2 完整接入时绑定（复用 A 骨架或独立前缀 /api/quant/engines/A2/*）。
5. **server.js 无 git 基线**：R-259 S0.0（git 基线）至今未执行（778,323 字节文件无版本控制）。改法：优先补 S0.0 基线提交，是一切看板改动的回滚前提（治理级纠正）。
6. **单 active 假设残留**：/api/quant/registry 仍可能多 active 取 created_at 最新（R-256 L2410）；engines.json 已提供显式映射，看板应改用 engines.json 作为引擎→registry 线的唯一真源（R-259 §4.2）。
