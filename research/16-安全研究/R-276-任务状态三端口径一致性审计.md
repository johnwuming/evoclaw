## 四、冲突清单（按严重度）

### 高-1：running→pending_review 的写入方未成文，三处假设互相矛盾（今日事故②的制度性根因）

- **现象**：0441/0442 断线后卡 running 6.5h；jsonl 里 0441 事后有回执、0442 至今没有。
- **证据**：① server.js 对 `.task-completions.jsonl` **零引用**（grep 全文 0 命中）；② heartbeat.sh:28-37 `sync_completions()` 空操作，注释声称同步"改由任务中心自身（subagent 写回执时）或主 agent 处理"——"任务中心自身"从未实现；③ 模板 `tools/templates/spawn-task.md`（自称"唯一来源"）完成回报段**只有 jsonl 写入，没有 PUT pending_review 步骤**；④ 实际现行为：主 agent 在任务书里 ad-hoc 加"完成后 PUT status=pending_review"（本任务书即有）——协议活在口头，不在模板。
- **后果**：任何一次主 agent 忘了写这行 ad-hoc 指令，或子 agent 中途死亡（正是 0441/0442），任务即悬挂 running，只能等第6条 90min 僵尸兜底。jsonl 已积累 151 行从未被消费（含 task-0362×3 重复回报），当前 141 个有回执任务 DB 全为终态——真空暂无存量伤害，但纯靠 ad-hoc+补丁兜。
- **涉及**：heartbeat.sh:28-37 / spawn-task.md 完成回报段 / server.js（缺失）。

### 高-2：PUT /api/tasks/:id 无状态白名单，且关键流转无事件痕迹

- **现象/风险**：任意字符串可入库为 status（DB 无 CHECK :143，handler 无校验 :944-945）；typo（如 `pendingreview`）会静默造出新状态，前端 fallback 显示原串(:7963)。且流转事件不全：写 pending_review **无 addEvent**；running→pending 僵尸退回**无 addEvent 且不清 dispatched_at**（对比 retry :963-967 会清）。
- **证据（DB 实例）**：task-0442 现状 status=pending、dispatched_at=15:44 残留、事件史止于 15:44 dispatched——退回动作零痕迹，事后无法区分"僵尸退回"与"随手改状态"。
- **涉及**：server.js:921-960、:143。

### 中-1：spawn_owner 语义已死，标签系统性失真（今日事故①根因）

- **定义**（:275-278 迁移注释）：'web'=dispatch 自动调度；'main'=主 agent 原生 spawn。dispatch.js 2026-08-14 已停用，"dispatch 自动调度"不存在了。
- **实际**：POST :860 对一切非 'main' 输入（含缺省）落 'web'——网页注册、cron、心跳 lane、主 agent 忘传参，全部标 'web'。
- **DB 交叉统计**：总数 web 344 / main 31；**有 agent_session_key（=主agent spawn 路径回写）的任务中 130 个标 web、18 个标 main——88% 错标**。session-key 端点事件文案就叫"主agent原生spawn回写"(:1059) 却不翻转 spawn_owner。本任务 task-0445（主 agent spawn）此刻同样标 'web'。
- **后果**：spawn_owner 不能回答"这任务谁派发的"；主 agent 据此误读来源即事故①。

### 中-2：僵尸退回通道复用 PUT，产出脏数据

僵尸退回（HEARTBEAT 第6条"产物中断→标记 pending 退回"）实际只能用 PUT status=pending 执行 → 不清 dispatched_at、无事件、retry_count 不增（见高-2 的 0442 证据）。最小改动是改走 /api/tasks/:id/retry（已具备三件套）或在 PUT 分支补齐。

### 中-3：updated_at 作为僵尸判据存在"洗白"通道

HEARTBEAT 第6条判据 = updated_at>90min。但 PUT 任何字段（改 notes、补 source_session 等）都会刷新 updated_at(:958)；执行期间无任何进度写入方。主 agent 在僵尸窗口内做一次无关编辑，计时即重置 90min。且时间戳为分钟级字符串（nowCST :316-320），无秒——精度可接受，但"编辑时间≠执行活跃时间"的语义混用要写进契约认知。

### 低-1：HEARTBEAT 第6条 `GET /api/tasks?limit=100` 参数被服务端忽略

GET /api/tasks 只支持 project_id/status/type（:805-830），limit 静默丢弃，返回全量 375 条。功能可用（running 过滤后量小），契约文案与实现不符。

### 低-2：前端/统计口径比状态机少 3 态 + 文档过时

筛选项缺 paused/cancelled（:6965-6974）；/api/stats totals 只循环 6 态且 total 排除 paused/cancelled 但也不含 pending_review/rejected/failed_final（:1296-1298）；CLAUDE.md 状态机 4 态。均为展示/文档层不一致，不影响流转。

### 低-3：pending_review 进入时不写 completed_at

:944-950 仅 done 分支写 completed_at；待审卡片"完成时间"多数为空（前端 :7987 已判空兜底）。语义上 completed_at=审核通过时间，与卡片文案"完成"有轻微歧义，可不修。

### 附：非冲突的设计取舍（记录备查）

- PUT/retry 无鉴权但服务仅绑 127.0.0.1:8055（:6204）：本地子 agent 可直写任意状态（含 done）。当前信任模型（子 agent 按任务书自律 + 事件表留痕）下可接受；若未来子 agent 有不可信输出需收紧。
- 心跳 v3"零写权"与第6条"处置后退回/验收"不矛盾：处置动作由主 agent（心跳唤醒后）执行，心跳 lane 本身仍零写——三端里这一点是自洽的。✓
