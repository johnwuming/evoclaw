## 1. 调研概述

### 1.1 需求背景

项目需要一套支付收费模块，实现：
- **支付通道**：支付宝 + 微信支付双通道收款
- **付费解锁**：通过API门控（API Gating）机制，控制功能/服务的付费解锁
- **商业模式**：免费基础功能 + 付费高级功能（Freemium/订阅制）
- **自主可控**：优先基于开源方案二次开发，降低成本和授权风险

### 1.2 调研方法

- 检索 GitHub/Gitee 主流开源支付系统项目
- 对比各项目的技术栈、功能覆盖、授权协议、社区活跃度
- 分析支付渠道官方接入费用与费率
- 结合行业外包开发报价数据，给出开发周期与成本估算
- 参考 SaaS API门控（Paywall/Feature Gating）最佳实践

### 2.2 详细项目分析

#### 2.2.1 DaxPay（推荐⭐）

- **来源**: Dromara 开源社区（dromara/dax-pay）
- **定位**: 企业级开源支付管理系统 / 支付网关
- **亮点**:
  - 架构清晰：商户端 + 运营端 + 收银台H5/小程序
  - 统一HTTP接口封装，业务系统对接简单
  - 支持RSA公私钥签名，交易安全
  - 多商户 + 服务商模式
  - 商业版提供进件、分账、分润、代理商系统
- **版本对比**:

| 版本 | 价格 | 功能 |
|---|---|---|
| 开源版 | 免费 | 基础支付（微信/支付宝）、退款、源码开放、社区支持 |
| 商业版 Plus | 联系销售（估2-5万/年） | + 进件、分账、分润、代理商、终端报备、费率管理 |
| SaaS版 | 联系销售 | 企业级云端、多租户、源代码授权 |

#### 2.2.2 Jeepay（推荐⭐）

- **来源**: 计全科技（jeequan/jeepay），原 XxPay 团队
- **定位**: 面向互联网企业的开源聚合支付系统
- **亮点**:
  - 支持普通商户模式 + 多渠道服务商模式
  - 已对接微信支付、支付宝、云闪付官方接口
  - 聚合码支付支持
  - 多MQ可切换（RocketMQ/ActiveMQ/RabbitMQ）
  - 提供 Java SDK、Python SDK、PHP Demo
  - Docker Compose 一键部署 + 宝塔面板安装
  - AI 接入助手（Jeepay Skills for Claude/Cursor）
  - 官方托管服务"计全付"可免自建
- **版本对比**:

| 版本 | 价格 | 功能 |
|---|---|---|
| 开源版 | 免费 (LGPL-3.0) | 支付/退款/聚合码/多商户/服务商模式 |
| Jeepay Plus | 联系销售 18611727422 | + 多端进件、灵活分账、30+渠道、硬件设备、代理展业 |
| 计全付（托管） | 按交易费率 | SaaS模式，免部署，100%全额分账 |

#### 2.2.3 独角数卡 Dujiaoka

- **来源**: assimon/dujiaoka（已归档 2026.03），继任者 Dujiao-Next（Go重写）
- **定位**: 自动发卡/虚拟商品售货系统
- **特点**: 开箱即用、多支付渠道、模板可换、1.1万星
- **适用**: 发卡网、虚拟商品销售，非通用支付系统
- **支付对接**: 通过 PayJS、易支付、码支付等间接接入

#### 2.2.4 彩虹易支付 EPay

- **来源**: 郑州追梦网络（lopinx/epay）
- **定位**: 免签约聚合支付网关
- **特点**: 支持支付宝/微信/QQ钱包、USDT插件、商户管理、通道轮询
- **注意**: 非真正开源（源码可获取但有限制），合规风险较高
- **适用**: 个人站长快速收款

#### 2.2.5 YunGouOS

- **来源**: YunGouOS/YunGouOS-PAY-SDK
- **定位**: 基于微信/支付宝官方服务商模式的支付SDK
- **特点**: 支持个人用户签约（无需营业执照）、多语言SDK
- **收费**: 一次性开通费，推广期无交易服务费
- **适用**: 个人开发者、个体户

## 3. 支付宝+微信支付接入方案

### 3.1 官方直连接入

| 项目 | 支付宝 | 微信支付 |
|---|---|---|
| **申请条件** | 企业/个体户营业执照 | 企业/个体户营业执照 |
| **个人接入** | ❌ 不支持 | ❌ 不支持（服务商模式可） |
| **申请费用** | 免费 | 免费 |
| **交易费率** | 0.6% | 0.6%-1%（按类目） |
| **结算周期** | T+1 | T+1 |
| **API版本** | V3 (OpenAPI) | V3 (微信支付API v3) |
| **主要支付方式** | APP支付、扫码支付、H5支付、电脑网站支付 | APP支付、扫码支付、JSAPI、H5支付、小程序支付 |
| **技术文档** | opendocs.alipay.com | pay.weixin.qq.com |

### 3.2 服务商模式接入（推荐）

通过微信/支付宝官方服务商资质，代商户签约开户：

| 方案 | 优势 | 劣势 |
|---|---|---|
| **自建服务商** | 资金直达商户账户、自主可控 | 需服务商资质、开发量大 |
| **使用 YunGouOS** | 个人也可签约、一次接入 | 有开通费、依赖第三方 |
| **使用 Ping++** | 多渠道一次接入、SDK完善 | 商业收费、交易手续费叠加 |
| **使用 讣全付** | 免部署、100%分账 | 依赖第三方平台 |

## 4. API门控付费解锁功能设计

### 4.1 概念模型

API门控（API Gating）是指通过API调用的权限控制，实现：
- **功能分级**：免费版 / 基础版 / 专业版 / 企业版
- **用量限制**：API调用次数/频率限制
- **订阅验证**：验证用户订阅状态，未付费则拒绝/降级
- **即时解锁**：支付成功后实时激活功能

### 4.2 架构设计

```
┌─────────────────────────────────────────────────────┐
│                    客户端 / 前端                      │
│              (Web / APP / 小程序)                     │
└──────────────────────┬──────────────────────────────┘
                       │ API请求
                       ▼
┌─────────────────────────────────────────────────────┐
│                  API 网关层                          │
│  ┌─────────┐  ┌──────────┐  ┌─────────────────┐   │
│  │ 认证/鉴权 │→│ 订阅状态  │→│ 功能门控决策     │   │
│  │ Token校验│  │ 检查     │  │ (Entitlement)   │   │
│  └─────────┘  └──────────┘  └────────┬────────┘   │
│                                       │             │
│              ┌────────────────────────┼───┐        │
│              │   允许 → 放行           │   │ 拒绝   │
│              │   限额 → 限流           │   │→403   │
│              │   未付费 → 引导付款     │   │        │
│              └────────────────────────┘   └────────┘
└──────────────────────────────┬──────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────┐
│                  业务服务层                          │
│         (实际的API功能 / 数据处理)                    │
└─────────────────────────────────────────────────────┘
                               ▲
                               │ 支付回调
┌─────────────────────────────────────────────────────┐
│                  支付系统层                          │
│  ┌──────────┐  ┌──────────┐  ┌────────────────┐   │
│  │ 订单管理  │←│ 支付通道  │←│ 回调处理        │   │
│  │          │  │ 支付宝/微信│  │ →更新订阅状态   │   │
│  └──────────┘  └──────────┘  └────────────────┘   │
└─────────────────────────────────────────────────────┘
```

### 4.3 核心数据模型

```
用户 (User)
├── id, username, email, created_at
├── subscription_tier (free/basic/pro/enterprise)
├── subscription_expires_at
└── api_quota_remaining

订阅套餐 (Plan)
├── id, name, price, billing_cycle (monthly/yearly/lifetime)
├── features (JSON: 允许的功能列表)
├── api_call_limit (API调用次数限制)
└── rate_limit (频率限制/分钟)

订单 (Order)
├── id, user_id, plan_id, amount, channel (alipay/wechat)
├── status (pending/paid/expired/refunded)
├── payment_id, paid_at
└── callback_data

功能权限 (Entitlement)
├── user_id, feature_key
├── granted_at, expires_at
└── source (subscription/payment/admin)

API调用日志 (ApiCallLog)
├── user_id, endpoint, timestamp
├── status (allowed/blocked/upgraded)
└── response_time
```

### 4.4 门控流程（时序）

```
用户请求API
    │
    ├─→ 1. Token认证（JWT/Session）
    │      └─ 失败 → 401 Unauthorized
    │
    ├─→ 2. 查询用户订阅状态
    │      └─ 过期/无订阅 → 检查是否免费功能
    │           ├─ 是免费功能 → 放行
    │           └─ 是付费功能 → 返回402 + 引导付款链接
    │
    ├─→ 3. 检查功能权限（Entitlement）
    │      └─ 无权限 → 403 + 提示升级套餐
    │
    ├─→ 4. 检查用量配额
    │      └─ 超限 → 429 + 提示购买更多额度
    │
    ├─→ 5. 频率限制（Rate Limiting）
    │      └─ 超频 → 429 + Retry-After
    │
    └─→ ✅ 放行 → 调用业务逻辑 → 返回结果

支付成功回调:
    支付成功 → 更新订单状态 → 激活订阅/解锁功能
    → 推送WebSocket通知前端刷新 → 用户即时获得功能
```

### 4.5 参考实现方案

#### 方案一：基于开源支付系统 + 自建门控层

```
DaxPay / Jeepay（支付网关）
        │ HTTP回调
        ▼
自建门控中间件（Node.js / Java / Go）
        ├── 订阅管理模块
        ├── 权限校验中间件
        ├── 用量统计 + Redis限流
        └── 管理后台（Vue/React）
                │
                ▼
        业务API服务
```

**优势**: 完全自主可控、数据不外泄、无第三方依赖  
**劣势**: 开发量大、需自行维护支付通道

#### 方案二：使用第三方订阅管理 + 支付

```
Stripe Billing / Paddle / Lemon Squeezy（国际）
        │ Webhook
        ▼
自建API网关（门控层）
        ├── 接收Webhook更新订阅状态
        ├── 权限校验
        └── 业务API
```

**优势**: 支付/订阅/税务全托管、开发量小  
**劣势**: 国际支付为主、费率5%+、资金在海外

#### 方案三：国内SaaS平台方案（混合）

```
支付宝/微信直连（通过DaxPay/Jeepay）
        │
        ▼
自建订阅+门控系统
        ├── 订阅生命周期管理
        ├── Feature Flag 控制台
        ├── API调用计量
        └── 管理后台
```

**优势**: 适合国内市场、费率低（0.6%）  
**劣势**: 需自行实现订阅管理逻辑

### 7.2 综合推荐方案

```
├── 数据库: MySQL 8.0 + Redis 7
├── 部署: Docker Compose
└── 监控: Prometheus + Grafana

开发计划:
Phase 1 (Week 1-3): Jeepay部署 + 支付渠道接入 + 基础收银台
Phase 2 (Week 4-6): 订阅套餐管理 + API门控中间件

预计投入: 8-12万 (标准版)

```

## 8. 风险与合规

### 8.1 支付合规要点

| 风险项 | 说明 | 应对 |
|---|---|---|
| **二清风险** | 资金经过平台再分发给商户 | 使用官方分账功能/银行存管 |
| **无证经营支付** | 未持支付牌照开展支付清算业务 | 仅做技术对接，资金直连商户 |
| **个人收款合规** | 个人二维码收款用于经营 | 通过服务商模式正规签约 |
| **数据安全** | 支付数据泄露 | PCI-DSS参考/加密存储/脱敏 |
| **税务合规** | 收入申报与开票 | 对接电子发票系统 |

### 8.2 开源协议风险

| 项目 | 协议 | 商用注意 |
|---|---|---|
| DaxPay | LGPL v3.0 | 修改后的代码必须开源，可作为独立服务调用 |
| Jeepay | LGPL-3.0 | 同上，修改代码需开源 |
| 独角数卡 | MIT | 最宽松，可任意使用 |
| 彩虹易支付 | 非标准开源 | 需购买商业授权，不可随意商用 |

> **⚠️ LGPL 注意**: 使用 LGPL 协议的支付系统作为独立服务部署（不改源码），通过 HTTP 接口调用，通常不触发开源义务。但如果修改了核心源码并分发，需要开源修改部分。

### 8.3 建议的合规路径

1. **企业主体**: 注册公司，获取营业执照
2. **支付资质**: 申请支付宝/微信商户号（企业资质）
3. **ICP备案**: 网站域名完成ICP备案
4. **数据保护**: 遵循《个人信息保护法》《数据安全法》
5. **支付安全**: 实施签名验签、防重放、HTTPS传输
6. **资金安全**: 不触碰资金流，仅做信息流转发
