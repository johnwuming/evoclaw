## 1. 问题定义与现状分析

### 1.1 什么是提示词遵从性？

提示词遵从性（Prompt Compliance / Instruction Adherence）是指大语言模型在接收到用户或系统指令后，**严格按照指令中定义的流程、约束、格式和优先级执行任务**的能力。

典型失败模式包括：

| 失败类型 | 表现 | 实际案例 |
|---------|------|---------|
| **流程跳过** | 跳过必需的前置步骤，直接执行后续操作 | 未录入任务中心就开始执行任务 |
| **约束违反** | 违反明确禁止的行为 | 被告知"不要执行未记录的任务"仍然执行 |
| **格式偏离** | 输出格式不符合要求 | 要求 JSON 输出但返回自然语言 |
| **优先级倒置** | 低优先级指令覆盖高优先级指令 | 软建议覆盖了硬约束 |
| **指令遗忘** | 长对话中忘记早期设定的重要规则 | 第10轮对话中不再遵守第1轮设定的规则 |

### 1.2 问题根因

大模型提示词遵从性不佳的深层原因：

1. **训练目标的偏差**：基础模型以"下一个 token 预测"为训练目标，天然倾向于生成"最可能的"而非"最合规的"输出
2. **指令理解的模糊性**：自然语言指令本身存在歧义，模型可能对"必须"、"应该"、"建议"等词的严重性理解不一致
3. **注意力衰减**：Transformer 架构中，长上下文里早期 token 的注意力权重会随对话进行而衰减
4. **偏好偏差**：模型在训练过程中可能学到了"尽快帮助用户"的偏好，导致跳过验证步骤
5. **缺乏外部约束**：纯文本提示词是"软约束"，没有硬性的执行阻断机制

## 2. Prompt Engineering 技巧

### 2.1 结构化提示词

将提示词从自然语言段落改为**结构化的分段格式**，是目前最有效的 prompt-level 方法。

**推荐结构（CRISP 框架）**：

```
[ROLE]          → 角色定义
[CONTEXT]       → 背景信息
[RULES]         → 硬约束规则（必须遵守）
[STEPS]         → 执行步骤（按序执行）
[OUTPUT_FORMAT] → 输出格式要求
[EXAMPLES]      → Few-shot 示例
```

**实际对比**：

❌ 差的写法：
> 你是一个研究助手，请先检查任务中心有没有记录，如果没有就不要执行。完成研究后把结果放到 shared/results 目录下。

✅ 好的写法：
```
[ROLE] 你是研究团队 Agent

[RULES]
- R1（硬约束）：不执行未记录在任务中心（tasks.db）的任务
- R2（硬约束）：所有研究产出存入 shared/results/ 目录
- R3（硬约束）：完成后必须写入 .task-completions.jsonl

[STEPS]
1. 收到任务 → 查询 tasks.db 确认任务存在
2. 任务不存在 → 拒绝执行，提示主 Agent 录入
3. 任务存在 → 执行研究
4. 完成研究 → 写入 shared/results/
5. 最终步骤 → 写入 .task-completions.jsonl
```

### 2.2 约束前置

将最重要的约束放在提示词的**开头和结尾**（首因效应 + 近因效应）：

```
# ⚠️ 铁律（违反任何一条即终止执行）
1. 不执行未录入任务中心的任务
2. ...

# ... 中间是正常提示词内容 ...

# ⚠️ 再次提醒：执行任何操作前，必须先确认任务已在任务中心
```

**原理**：Transformer 的注意力机制对序列首尾的 token 分配更高权重。首尾重复关键约束可显著提高遵从率。

### 2.3 Few-shot 示例

提供正例和反例，让模型通过上下文学习正确的执行模式：

```
# 示例

## 正确行为
用户: "帮我调研 XX"
Agent: "让我先检查任务中心... 查询到任务 task-xxx，开始执行。"

## 错误行为（禁止）
用户: "帮我调研 XX"
Agent: "好的，我马上开始调研。"  # ← 错误：未检查任务中心
```

### 2.4 Chain-of-Thought (CoT)

对于复杂任务，要求模型在执行前**显式推理**：

```
在执行任何操作前，请先完成以下检查清单：
1. 这个任务是否在任务中心有记录？→ [是/否]
2. 如果否，停止执行并提示录入
3. 如果是，记录任务 ID
4. 确认执行范围和产出要求
5. 确认无误后，开始执行
```

**注意**：CoT 在硬约束场景中要谨慎使用——推理链可能"合理化"跳过约束的行为。建议将硬约束检查放在 CoT **之前**，作为独立的门控步骤。

### 2.5 负面约束的精确写法

负面约束（"不要做 X"）的效果不如正面约束（"在做 X 之前，必须先做 Y"）。

| 负面写法 | 正面替代 | 效果差异 |
|---------|---------|---------|
| "不要执行未记录的任务" | "执行任务前，必须先查询 tasks.db 确认任务存在" | 正面写法遵从率高 15-20% |
| "不要忘记写完成报告" | "任务完成的标志是写入 .task-completions.jsonl" | 正面写法更可靠 |
| "不要跳过验证步骤" | "每个步骤完成后，运行 verify() 检查" | 正面写法更可执行 |

**原理**：模型在处理"不要做 X"时，需要先表征 X 再否定它，这个否定操作在生成过程中可能被"跳过"。

## 3. 模型层面改进

### 3.1 指令微调（Instruction Tuning / SFT）

**核心思想**：在基础模型上用 `(instruction, output)` 配对数据进行监督微调，弥合"下一个 token 预测"与"遵循人类指令"之间的差距。

**关键研究**：Zhang et al. (2023) 在 Instruction Tuning Survey 中系统总结了该方法，指出 SFT 能显著提升模型的指令遵循能力，且效果与指令数据的**质量和多样性**正相关，而非单纯数量。

**实践要点**：
- 指令数据应包含**多难度层级**（简单指令、复合指令、约束冲突指令）
- 应包含**负面示例**（违反约束的输出被标注为"差"）
- 高质量的小数据集（如 1K 条精标数据）效果可能优于低质量的大数据集

**参考实现**：WizardLM (Xu et al., 2023) 提出 Evol-Instruct，通过 LLM 自动演化指令复杂度，生成不同难度层级的训练数据，使模型在复杂指令上的遵从能力大幅提升。

### 3.2 RLHF（Reinforcement Learning from Human Feedback）

**核心思想**：收集人类对模型输出的偏好排序，训练奖励模型，再用 PPO 等 RL 算法优化模型。

**关键研究**：InstructGPT (Ouyang et al., 2022) 证明了 RLHF 能让 1.3B 参数模型的指令遵循能力超过 175B 的基础 GPT-3。

**对 Prompt Compliance 的影响**：
- RLHF 能让模型学会区分"有帮助"与"顺从用户所有要求"的差别
- 通过奖励设计可以**强化流程遵从**：例如对"先验证再执行"的行为给予更高奖励
- **风险**：过度优化可能导致模型变得过于保守（refusal 行为增加）

### 3.3 DPO（Direct Preference Optimization）

**核心思想**：跳过奖励模型和 RL 训练循环，直接用偏好数据通过分类损失优化模型。

**关键研究**：Rafailov et al. (2023) 提出 DPO，证明其效果与 PPO-RLHF 相当或更好，且训练更稳定、实现更简单。

**对 Prompt Compliance 的实践意义**：
- 可以专门构建"遵从约束 vs 跳过约束"的偏好对来微调模型
- 训练成本低，适合中小团队定制化提升特定场景的遵从性
- 例如：构造 `(instruction_with_rules, compliant_output, non_compliant_output)` 三元组

### 3.4 Constitutional AI

**核心思想**：让 AI 用一组"宪法"原则自我评判和修正，减少对人类标注的依赖。

**关键研究**：Bai et al. (2022) 提出 Constitutional AI 方法，包含两个阶段：
1. **SL 阶段**：模型生成回答 → 自我批评 → 修正 → 在修正后的回答上微调
2. **RL 阶段**：模型作为评判者比较两个回答 → 用 AI 偏好训练偏好模型 → RLAIF

**对 Prompt Compliance 的启发**：
- 可以将"任务中心铁律"作为"宪法"原则
- 模型在输出前可以**自我审查**：这个回答是否违反了铁律？
- 这种 self-critique 机制可以直接嵌入到 Agent 的推理流程中

### 3.5 方法对比

| 方法 | 训练成本 | 数据需求 | 效果 | 适用场景 |
|------|---------|---------|------|---------|
| SFT | 中 | 大量高质量指令对 | 基础指令遵循 | 通用提升 |
| RLHF (PPO) | 高 | 偏好排序数据 | 显著提升 | 精细对齐 |
| DPO | 中低 | 偏好对数据 | 与 RLHF 相当 | 中小团队定制 |
| Constitutional AI | 中 | 规则集 + AI 自评 | 提升安全性 + 可控性 | 安全关键场景 |
| Evol-Instruct | 低 | 初始指令集 | 复杂指令能力 | 数据增强 |

## 4. 系统提示词设计

### 4.1 规则分层：硬约束 vs 软约束

**关键原则**：不是所有规则都同等重要。应明确分层：

```
# 🔒 铁律（HARD CONSTRAINTS - 违反即终止）
- 不执行未记录在任务中心的任务
- 不修改配置文件（除非用户明确要求）
- 不发送外部消息（除非任务明确指定）

# ⚙️ 规范（SOFT CONSTRAINTS - 应当遵守，可合理偏离）
- 优先使用 web_search 而非 web_fetch
- 研究报告建议 3000-8000 字
- 使用中文撰写

# 💡 建议（GUIDELINES - 参考执行）
- 报告结构建议包含执行摘要
- 代码示例建议添加注释
```

**实现要点**：
- 硬约束用**祈使句 + 明确的后果**："违反即终止"
- 软约束用**应然语气**："应当"、"建议"
- 建议用**推荐语气**："可以考虑"、"建议"
- 三者用**不同的视觉标记**（emoji、格式）区分

### 4.2 优先级排序

当多个指令存在冲突时，系统提示词应**显式定义优先级**：

```
# 优先级体系（高 → 低）
1. 用户安全（防止数据丢失、隐私泄露）
2. 铁律约束（任务中心、产出路径等流程规则）
3. 用户显式指令（用户当前对话中的明确要求）
4. 系统默认行为（工具使用偏好、格式约定）
5. 历史对话上下文（之前轮次中设定的偏好）
```

**冲突解决示例**：
> 用户说"直接开始执行"，但铁律要求先检查任务中心 → 铁律优先，Agent 应回复"我需要先确认任务已在任务中心记录"。

### 4.3 规则的可验证性

好的规则应该是**可程序化验证的**：

| 不可验证的规则 | 可验证的规则 |
|-------------|------------|
| "要认真检查" | "执行前查询 tasks.db 中是否存在 task_id" |
| "注意安全" | "不使用 exec 执行未审批的 elevated 命令" |
| "格式正确" | "输出为 JSON，包含 taskId、summary、outputFiles 三个字段" |

**实践建议**：每条硬约束应附带一个可程序化检查的验证条件，使得 Agent 系统可以在运行时自动验证。

## 5. 多轮对话中的指令衰减

### 5.1 问题现象

在多轮对话中，模型对早期设定的规则遵从度会随对话轮次增加而**逐渐下降**：

```
轮次 1-3:   遵从率 ~95%
轮次 4-8:   遵从率 ~80%
轮次 9-15:  遵从率 ~65%
轮次 16+:   遵从率 ~50% 或更低
```

**根因**：
1. **注意力衰减**：随着上下文增长，早期 token 的注意力权重被稀释
2. **上下文窗口限制**：超出窗口后早期指令被截断
3. **近因偏好**：模型更关注最近几轮对话，倾向于满足"眼前的请求"而忽略"远处的规则"

### 5.2 解决方案

#### 5.2.1 规则重注入（Rule Re-injection）

在每 N 轮对话后，由系统自动重新注入关键规则：

```
# 系统在每轮对话后自动添加的上下文
[系统提醒] 当前执行的铁律：
1. 不执行未录入任务中心的任务
2. 产出存入 shared/results/
3. 完成后写入 .task-completions.jsonl
```

**OpenClaw 实践**：可以在 Agent 的配置中设置 `ruleRefreshInterval: 5`，每 5 轮自动重注入。

#### 5.2.2 上下文压缩与关键信息保留

不保留完整对话历史，而是：
- 保留**系统提示词**（永不截断）
- 保留**最近 N 轮**完整对话
- 将更早的对话压缩为**摘要**
- 摘要中显式包含"已设定的规则"和"已完成的步骤"

#### 5.2.3 状态外置（External State Tracking）

将关键状态存到外部存储而非依赖对话上下文：

```python
# 不依赖对话记忆，而是查外部状态
def check_before_execute(task_id):
    if not task_exists_in_db(task_id):
        return "拒绝执行：任务未在任务中心记录"
    if not rule_compliance_verified(task_id):
        return "拒绝执行：规则验证未通过"
    proceed(task_id)
```

**这是最可靠的方案**——将"记住规则"从"模型记忆"转移到"程序逻辑"。

#### 5.2.4 对话分段（Conversation Chunking）

将长对话拆分为多个短段，每段开始时重新加载完整规则：

```
[Session 1: 任务理解] → 加载完整规则 → 确认理解
[Session 2: 任务执行] → 加载完整规则 → 执行
[Session 3: 结果验证] → 加载完整规则 → 验证
```

## 6. Agent 架构层面

### 6.1 工具调用纪律（Tool Call Discipline）

**问题**：Agent 在调用工具时可能跳过前置检查，或以错误的顺序调用工具。

**解决方案**：在工具层面实现**前置条件检查**：

```python
# 工具定义中包含前置条件
@tool(preconditions=[check_task_exists, check_user_authorized])
def execute_research(topic: str, output_path: str):
    """执行研究任务"""
    ...
```

如果前置条件不满足，工具层直接拒绝调用，不依赖模型"自觉"遵守。

### 6.2 流程编排（Workflow Orchestration）

将"必须按顺序执行"的步骤编码为**状态机**而非依赖模型判断：

```
状态机定义：
[INIT] → check_task_center → [VERIFIED] → execute_task → [COMPLETED] → write_completion → [DONE]
                         ↓
                    [REJECTED] → notify_main_agent → [END]
```

**实现方式**：
- 使用 TaskFlow 或类似的状态机框架
- 每个状态转换有明确的**进入条件**和**退出条件**
- 模型只能在当前状态允许的动作集合中选择

### 6.3 检查清单机制（Checklist Mechanism）

在 Agent 执行前强制完成检查清单：

```
# 执行前检查清单（每项必须通过才能继续）

□ 任务已在任务中心记录？     → [✓/✗]
□ 产出路径已确认？          → [✓/✗]
□ 执行范围已明确？          → [✓/✗]
□ 安全约束已检查？          → [✓/✗]

如有任何 ✗，停止执行并报告原因。
```

**实现建议**：可以将检查清单作为系统提示词的一部分，要求模型在输出实际执行内容前，先输出检查清单的结果。

### 6.4 Self-Verification（自我验证）

在 Agent 完成任务后、返回结果前，增加一个**自我验证步骤**：

```
# 任务完成后的自我验证

请在输出最终结果前，完成以下验证：
1. 我是否确认了任务在任务中心存在？ → [引用查询结果]
2. 产出文件是否已写入正确路径？ → [引用文件路径]
3. 是否已写入 .task-completions.jsonl？ → [引用写入内容]
4. 是否违反了任何铁律？ → [逐条检查]

如发现问题，请修正后再输出。
```

### 6.5 双 Agent 校验

对于关键流程，使用两个 Agent 互相校验：
- **执行 Agent**：负责执行任务
- **审核 Agent**：检查执行过程是否合规

这种模式类似代码开发中的 PR review 机制。

### 6.6 架构图：多层防护

```
用户请求
    ↓
┌─────────────────────────────────┐
│  Layer 1: 系统提示词（规则定义）  │  ← 软约束
├─────────────────────────────────┤
│  Layer 2: 前置检查（程序逻辑）    │  ← 硬约束
│  - 任务中心查询                   │
│  - 权限验证                      │
├─────────────────────────────────┤
│  Layer 3: 状态机（流程控制）      │  ← 流程约束
│  - 只允许当前状态的合法动作        │
├─────────────────────────────────┤
│  Layer 4: 模型推理（执行）        │  ← 模型能力
├─────────────────────────────────┤
│  Layer 5: 后置验证（自我审核）    │  ← 结果约束
│  - 检查清单                      │
│  - 铁律复核                      │
└─────────────────────────────────┘
    ↓
最终输出
```

**核心原则**：**永远不要只依赖模型自觉。将关键约束在架构层面硬化。**

## 7. 业界最佳实践

### 7.1 Anthropic（Claude）

Anthropic 在 Claude 的设计中采用了以下策略：

1. **Constitutional AI**：通过"宪法"原则让模型自我约束（Bai et al., 2022）
2. **系统提示词优先级**：Claude 的系统提示词明确将安全规则置于最高优先级
3. **XML 标签结构化**：使用 `<instructions>`、`<rules>` 等 XML 标签结构化提示词，提高模型对指令边界的识别
4. **prefill 技术**：通过预填充模型输出的开头来引导其遵循特定格式或流程
5. **长上下文管理**：Claude 支持超长上下文（200K+），但建议将关键规则放在系统提示词中而非对话历史中

**可借鉴实践**：
- 使用 XML 标签组织提示词结构
- 关键规则放在系统提示词中（持久存在），而非对话中（可能被遗忘）
- 利用 prefill 引导模型先执行检查再执行任务

### 7.2 OpenAI（GPT 系列）

OpenAI 的方法以 RLHF 为核心：

1. **InstructGPT 范式**（Ouyang et al., 2022）：SFT → 奖励模型 → PPO 三步训练
2. **结构化输出**：通过 Function Calling / Structured Output 强制模型按特定格式输出
3. **系统消息分层**：system / developer / user 三级消息优先级
4. **内容审核**：独立的 moderation 模型作为外置约束

**可借鉴实践**：
- 使用 Function Calling 约束模型的输出格式和可用动作
- 分层消息优先级（system > developer > user）
- 独立的外置审核机制

### 7.3 Google（Gemini）

1. **多模态指令遵循**：在文本、图像、音频等多种模态上保持指令一致性
2. **安全设置层级**：通过 Safety Settings API 提供可调节的约束强度
3. **Grounding**：将模型输出锚定到可信来源（Search Grounding、Vertex AI Search）

### 7.4 通用最佳实践总结

| 实践 | Anthropic | OpenAI | Google | 通用建议 |
|------|-----------|--------|--------|---------|
| 结构化提示词 | XML 标签 | JSON Schema | Safety Settings | ✅ 强烈推荐 |
| 规则前置 | 系统提示词 | system 消息 | 安全设置 | ✅ 强烈推荐 |
| 外置约束 | Constitutional AI | Moderation | Safety API | ✅ 推荐 |
| 状态外置 | - | Function Calling | Grounding | ✅ 推荐 |
| 自我验证 | Self-critique | - | - | ✅ 推荐 |
| 规则重注入 | 长上下文管理 | - | - | ✅ 推荐 |

## 8. 评估方法

### 8.1 量化评估指标

#### 8.1.1 指令遵从率（Instruction Compliance Rate）

```
遵从率 = (模型遵从指令的测试用例数 / 总测试用例数) × 100%
```

需要构建一个**指令遵从测试集**，包含：
- 简单指令（单步操作）
- 复合指令（多步操作，有顺序依赖）
- 约束指令（包含"必须"/"不要"的指令）
- 冲突指令（多个指令存在潜在冲突）
- 干扰指令（在关键指令间插入无关指令）

#### 8.1.2 约束遵循率（Constraint Satisfaction Rate）

针对每条约束单独评估：

```
约束 R1 遵循率 = (遵循 R1 的测试用例数 / 包含 R1 的总用例数) × 100%
```

#### 8.1.3 流程完整率（Workflow Completeness Rate）

```
流程完整率 = (正确执行的步骤数 / 应执行的总步骤数) × 100%
```

#### 8.1.4 指令衰减曲线（Instruction Decay Curve）

在多轮对话中，绘制遵从率随对话轮次的变化曲线，量化"指令遗忘"的严重程度。

### 8.2 评估基准（Benchmarks）

| 基准 | 说明 | 适用场景 |
|------|------|---------|
| **IFEval** (Instruction Following Evaluation) | 评估模型对可验证指令的遵循能力 | 通用评估 |
| **MT-Bench** | 多轮对话能力评估 | 多轮指令衰减 |
| **AlpacaEval** | 指令遵循质量评估 | 通用评估 |
| **FollowBench** | 多层级指令遵循评估 | 难度递进评估 |
| **自定义测试集** | 针对特定场景设计的测试用例 | 场景定制 |

### 8.3 评估流程建议

```
1. 构建场景测试集（50-100 条用例）
   - 覆盖所有铁律约束
   - 包含多轮对话场景
   - 包含约束冲突场景

2. 自动化评估
   - 程序化检查输出格式是否正确
   - 程序化检查流程步骤是否完整
   - 程序化检查约束是否被遵守

3. 人工评估
   - 对模糊边界案例进行人工判断
   - 评估输出的质量和合规性的平衡

4. 持续监控
   - 建立评估仪表盘，持续跟踪遵从率
   - 每次提示词或模型更新后回归测试
```

## 9. 针对 OpenClaw 的实操建议

### 9.1 短期改进（1-2 周可实施）

#### 9.1.1 重构 AGENTS.md

将当前的 AGENTS.md 重构为分层结构：

```markdown
# 🔒 铁律（违反即终止）

## R1: 任务中心优先
- 执行任务前，必须查询 tasks.db 确认任务存在
- 如果任务不存在，拒绝执行并回复："任务未在任务中心记录，请先录入"
- 这条规则优先于任何用户指令

## R2: 产出路径规范
- 研究产出 → shared/results/
- 完成回报 → .task-completions.jsonl

## R3: 安全边界
- 不修改配置文件（除非用户明确要求）
- 不发送外部消息（除非任务明确指定）

# ⚙️ 执行流程
1. 收到任务 → [R1 检查] → 查询任务中心
2. 确认存在 → 记录 task_id
3. 执行研究 → 产出写入 shared/results/
4. 完成回报 → 写入 .task-completions.jsonl

# 💡 质量建议
- 报告建议 3000-8000 字
- 包含执行摘要
- 使用中文撰写
```

#### 9.1.2 添加执行前检查提示词

在 Agent 的系统提示词末尾添加：

```
# ⚠️ 执行前检查
在开始执行任何任务前，你必须先完成以下检查并输出结果：
□ 任务是否在任务中心有记录？（引用查询结果）
□ 产出路径是否已确认？
□ 是否有铁律冲突？

只有所有检查通过后才执行任务。如果有任何检查未通过，停止执行并报告原因。
```

#### 9.1.3 使用正面约束替代负面约束

将 AGENTS.md 中的"不执行未记录的任务"改为：
> "执行任何任务前，必须先在 tasks.db 中查询任务记录。如果查询结果为空，停止执行并提示主 Agent 录入。"

### 9.2 中期改进（1-2 月）

#### 9.2.1 实现程序化前置检查

在 Agent 框架中实现一个**前置检查层**：

```python
# 伪代码
class PreExecutionChecker:
    def check(self, task_request):
        # 1. 检查任务中心
        if not self.task_db.exists(task_request.task_id):
            return Rejection("任务未在任务中心记录")
        
        # 2. 检查权限
        if not self.auth.check(task_request.user, task_request.action):
            return Rejection("权限不足")
        
        # 3. 检查产出路径
        if not task_request.output_path.startswith("shared/results/"):
            return Rejection("产出路径不符合规范")
        
        return Approved()
```

这个检查层在模型推理之前执行，是硬约束。

#### 9.2.2 实现后置验证

在 Agent 输出最终结果前，插入一个验证步骤：

```python
class PostExecutionValidator:
    def validate(self, task_result):
        checks = [
            ("任务中心记录", self.verify_task_completion_logged),
            ("产出文件存在", self.verify_output_files_exist),
            ("铁律无违反", self.verify_rules_not_violated),
            ("完成回报已写入", self.verify_completion_jsonl),
        ]
        for name, check in checks:
            if not check(task_result):
                return ValidationError(f"验证失败: {name}")
        return Valid()
```

#### 9.2.3 建立评估测试集

构建一个包含 50-100 条测试用例的遵从性测试集，用于：
- 每次提示词修改后回归测试
- 模型升级后的兼容性检查
- 量化追踪改进效果

### 9.3 长期改进（3-6 月）

#### 9.3.1 DPO 微调

收集"合规 vs 不合规"的执行案例对，用 DPO 微调模型：
- 合规案例：正确检查任务中心、按流程执行、正确写入产出
- 不合规案例：跳过任务中心检查、产出路径错误、忘记写入完成回报

#### 9.3.2 多 Agent 校验机制

实现执行 Agent + 审核 Agent 的双 Agent 架构：
- 执行 Agent 负责任务执行
- 审核 Agent 在执行前检查计划是否合规，在执行后检查结果是否合规
- 审核不通过则打回重做

#### 9.3.3 自适应规则重注入

根据对话轮次和任务复杂度，动态调整规则重注入频率：
- 简单任务：每 10 轮重注入一次
- 复杂任务：每 5 轮重注入一次
- 检测到约束提及频率下降时：立即重注入

> **报告总结**：提高大模型提示词遵从性是一个**多层级、系统工程**问题。单一层面的改进（如仅优化提示词或仅依赖模型能力）效果有限。最有效的策略是**多层防护**：在提示词层面用结构化格式和正面约束提高模型理解，在架构层面用程序化检查和状态机确保硬约束不被跳过，在模型层面通过 SFT/DPO 持续提升指令遵循能力。对于 OpenClaw 当前的问题，**短期优先实施 9.1 节的提示词重构和执行前检查**，**中期推进 9.2 节的程序化前置检查和后置验证**，可以显著减少"跳过任务中心"等流程违规问题。
