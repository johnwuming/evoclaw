# spawn-task.md — 子 agent 任务书模板（唯一来源）

> 主 agent 每次 spawn 必须读本模板生成任务书。
> 下方【上下文纪律】段必须**完整、原样**复制进 task prompt，不得改写或省略。
> 验收标准、完成回报格式只以本文件为准，不在其他文件重复定义。

---

## 任务书结构

```markdown
[一句话任务描述]

## 项目上下文
- 项目路径：[绝对路径]
- 当前状态：[已有实现 / 相关文件 / 数据契约]
- 关键约束：[依赖、接口、不得改动的部分]

## 质量要求
1. [针对本任务的具体要求]
2. 修改后必须运行测试或验证命令
3. 测试失败则修复，直到全部通过；不允许“应该可以”
4. 不要修改与任务无关的文件
5. 完成后输出：修改了哪些文件、测试/验证结果

## 验收标准（必须可执行）
- 验证命令：[命令]
- 预期结果：[可观察输出]

## 交付物
- 正式输出：[文件路径]
- 过程笔记：[shared/results/work/<task>-notes.md]

## 完成回报
完成后 MUST 将完成概要写入：
/root/.openclaw/workspace/scripts/.task-completions.jsonl
格式：{"taskId":"task-XXXX","summary":"改了什么、验证结果","outputFiles":["路径"]}
```

---

## 上下文纪律（硬约束，违反 = 任务失败）

> 主 agent 生成任务书时，把下面整段原样贴入任务书末尾：

```text
## 上下文纪律（硬约束，违反=任务失败）
1. 所有 curl 必须 `| head -c 2000` 截断；SSH 命令输出 ≤30 行（用 tail/grep/python 抽字段）
2. 读文件前先 `wc -c`：>30KB 禁止全读，用 head/tail/grep 或 python one-liner 只取需要的字段
3. 【边查边写】每完成一个核验/分析点，立即把结论追加写入 work 笔记文件（路径由任务书指定）。
   上下文如果丢失，笔记文件就是恢复点——不允许把证据只留在对话里
4. 同一大 JSON/API 响应禁止拉取第二次：第一次就落盘 /tmp/，之后用 python 逐字段读取
5. 报告撰写阶段只从笔记文件取材，不从记忆复述——防上下文膨胀后半途报废
6. 自检：如果你的累计工具输出感觉超过 ~200KB，立即停止探测，转入写报告/写笔记模式
```

## 分阶段与加强约束

| 信号 | 动作 |
|---|---|
| 3+ 文件的功能开发 | 分步 spawn，每步验证后再下一步 |
| 涉及数据库 schema | 任务书增加：先给迁移方案，不直接改库 |
| 涉及认证/安全相关代码 | 完成后额外验证；主 agent 独立复测 |
| 子 agent 报告测试失败但声称已修复 | 重新 spawn 验证 |
| 评审/红队类任务（易爆上下文） | 先 `wc -c` 评估对象；>50KB 先让子 agent 做摘要落盘，再基于摘要评审 |
| 大任务 | 拆「证据收集 → 撰写/实现 → 验证」两到三段，每段 fresh context |

## 主 agent 验收动作（不写进子 agent 任务书）

1. 查 `.task-completions.jsonl` 是否有完成概要。
2. 验证是否实际运行了测试/验证命令，而不是“应该可以”。
3. 检查修改范围：没有无关文件被改动。
4. 查看 `sessions_list` 的 `totalTokens`：>50 万需警惕，结论必须独立核验。
5. 检查过程笔记文件存在且内容能支撑结论。
